最近用 Claude 连着聊了很久的技术问题，越聊越累。不是它答错了，而是答案经常要读两三遍才明白。

## 先让它自己找原因

我直接问它：怎么才能让你每次都说得清楚易懂？

它翻了一遍我们前面的对话，总结出四个问题：

- **先讲概念，后举例子。** 比如我问一个多 agent 系统是怎么实现的，它一上来就列出"触发、线程、授权"这些概念，我读完还是不知道这东西在干什么。后来换成拿一个具体请求从头走一遍，我一下就懂了。
- **术语太多。** 代码里的名字、英文缩写，没解释就直接用。
- **太长。** 一个回答塞五六个小节、好几张表，重点被淹没了。
- **没先确认问题。** 好几次我说"不是这个意思"，因为它在猜我要问什么。

它也说了哪几次效果好：用类比（比如"像医院的分诊台"），拿一个具体场景从头走到尾，先说"你说对了一半"再补充。

## 九条规则太多了

然后它给了一份九条的规则：第一句先给结论、先举例再讲概念、术语第一次出现要解释、默认 3 到 5 个要点、一个回答只讲一件事、表格只用来对比、多用类比、没把握时先复述问题、区分事实和推断……

每条都对，但我看完的第一反应是：太复杂了。九条规则本身就要读好几遍，而且条数一多，它们之间还会打架。比如"默认简短"和"先举一个完整例子"，到底听谁的？

我真正在意的其实只有一件事：**每句话我读一遍就能懂。** 其他几条都是实现这件事的手段。

## 收成一句话

所以我让它改成一个标准，最后定下来是这样：

```markdown
# 回答风格

每句话都要让第一次接触这个话题的人读一遍就懂。读不懂就换个说法：用大白话、举具体例子，术语先解释再用。
```

第一句是唯一的标准，第二句是做不到时的三个补救办法。

为什么一句比九句好：

- **好检查。** 写完回头读一遍，看懂没看懂，一下就能判断。九条规则要逐条对照，模型和人都容易漏。
- **不会互相打架。** 只有一个目标，所有取舍都往"更好懂"这一边靠。
- **管得更宽。** 九条规则总有没覆盖到的情况，"读一遍就懂"什么情况都能用。

## 写进全局配置

Claude Code 每次开始对话，都会自动读取 `~/.claude/CLAUDE.md`，这是你个人的全局配置，对所有项目都生效。把上面那段加到这个文件末尾就行。

有几点需要知道：

- **只对新对话生效。** 正在进行的对话不会重新读这个文件，新开一个才会带上这条规则。
- **只在你自己的电脑上生效。** 这个文件存在你本机的用户目录里，团队里其他人用 Claude 不受影响。想让整个项目的人都用，就写到项目根目录的 `CLAUDE.md` 里，跟代码一起提交。
- **它是一条要求，不是开关。** 模型大部分时候会照做，偶尔也会写得绕。遇到这种情况直接说"没看懂，换个说法"，比再加一条规则管用。

回头看，这件事最有用的一步不是写规则，而是先让它把前面的对话翻一遍，找出到底哪里难懂。原因找准了，规则反而可以很短。
