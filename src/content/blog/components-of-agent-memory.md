[上一篇](/blog/agent-context-management/)记的是，一个长任务做到一半，上下文快满了该怎么办。这一篇接着看另一个问题：一次任务结束以后，Agent 怎么把学到的东西留到下一次。

材料是 Anthropic 在 2026 年 11 月 6 日发的一篇工程文章，[《The components of agent memory》](https://www.anthropic.com/research/components-of-agent-memory)。下面是我的阅读笔记，数字都对照原文核过。

## 先划清边界：什么算"记忆"

文章说的 Agent 记忆，是指 Agent 从过去的对话和任务里学到、并且能留到下一次会话的东西，保存成它之后能读的文字。

有三样东西不算：

- **训练时改动的模型参数**。那是模型本身变了，不是它"记住"了什么。
- **单次对话里临时学会的东西**。对话一结束就没了。
- **上下文压缩（Compaction）**。也就是上一篇讲的，为了让当前任务接着做下去，把旧内容总结掉。

## 从人脑借来的思路

文章开头引了克尔凯郭尔的一句话，大意是：人生只能往回看才能理解，却必须往前过。给 Agent 设计记忆也是一样：写下一条笔记的时候，你并不知道它以后有没有用。

人脑是这样分工的：

- **白天，海马体随时在记**。经历的事情很快形成记忆，马上就能用。
- **睡觉和安静休息的时候，大脑会"重放"最近的经历**。在这个过程中慢慢提炼，把一部分变成长期知识。

Agent 也可以这样分工：干活的时候随手记笔记；两次会话之间的空闲时间，再回头翻看工作记录，纠正错误、整理笔记。这个离线整理的过程，文章叫它 **Dreaming（做梦）**。思路来自 Letta 和加州大学伯克利分校提出的"睡眠时间计算"（sleep-time compute）：趁模型闲着的时候，让它整理自己已有的内容。

## 记忆的四个组成部分

从下往上看，大致可以分成四层：

| 层 | 是什么 | 作用 |
|---|---|---|
| 原始记录 | 完整的会话记录，包括每次工具调用和返回 | 事实依据，回头核对用 |
| 记忆笔记 | Agent 干活时主动写下的笔记文件 | 记下当时觉得重要的经验、规则和踩过的坑 |
| 记忆结构 | 从多份笔记里整理出来的东西，比如互相链接的 Wiki | 相当于一张地图，帮它在大量记忆里快速找到东西 |
| 预加载内容 | 每次新会话开始时，自动塞进上下文的那一小部分 | 一个很短的入口和索引，其余的需要时再去读 |

Dreaming 就是推动信息在这几层之间流动的东西：拿笔记去对照原始记录、找出写错的；合并重复的内容；搭建和更新 Wiki；决定哪些最重要的内容要提到最上面，每次都预加载。

## 发现一：记忆本质上是一种预测

写下一条规则，其实是在预测"这个情况以后还会出现"。写下一个核实过的事实，是在预测"以后的自己会想直接用它，不用再查一遍"。

文章用了一个评测集 CL-Bench 1.0 来测这件事。其中一个任务是：让 Claude 查数据库回答一连串问题，每答完一题就告诉它正确答案，它可以写笔记帮自己答后面的题。每道题都在一个全新的会话里做，唯一能带过去的，就是那个记忆文件夹。

理想的做法是形成一个学习闭环：答错了，记下来，猜原因，验证猜想，最后变成一条"以后该怎么答"的规则。不同代的模型，走到了不同的位置：

- **Sonnet 4.6**：只走到"猜原因"这一步。文件夹里散落着一堆文件，每个都写着几条没验证过的猜测。
- **Opus 4.7**：把笔记合并成一份参考文档，开始区分哪些已经核实、哪些还没确认。
- **Sonnet 5**：答案被判对以后标成"已确认"，答错了就写一条更正。
- **Opus 5**：第一个真正闭合了这个循环。大多数条目里都有规则、这条规则为什么成立、以前题目的答案，以及一路上发现的陷阱。Opus 5.5 和 Sonnet 5.5 也做到了。

## 发现二：记得少，反而走得远

这个实验是让 Claude 玩《宝可梦 红》。这个游戏流程很长，适合测试它"觉得什么值得记"。文章比较了两个模型各自玩到大约第一万步时的记忆文件夹。

- **Sonnet 3.7 什么都记**。每场战斗、每个道具、每个遇到的角色，经常都单独建一个文件，一共 413 个文件、225 个文件夹，只拿到 1 枚徽章（徽章代表游戏进度）。更糟的是，钱有多少、人在地图哪里，这些信息时刻在变，而且屏幕上随时能看到，记下来很快就过期了。它越来越多的时间花在翻笔记上，而不是玩游戏。有一段，它连续 17 步都在建文件、删文件，游戏里一步没动。
- **Fable 5 只记 9 个文件**，分在 2 个文件夹里，外加一个总览文件 `global.md`，拿到 4 枚徽章。`global.md` 像一块仪表盘，写着当前目标、打道馆的计划，以及它给自己定的记忆规则。Opus 5.5 用了类似的方法，直接通关了。

区别在于记的是什么。屏幕上随时能读到的东西，不用记。只有自己推理出来、不写下来就会丢的东西才值得记：目标、计划，以及试出来有效的策略。比如 Fable 5 连扔 7 个精灵球都没抓到鲤鱼王（游戏里最好抓的宝可梦之一），最后记下一条：连续 3 次以上失败，就在菜单操作之间多插几次等待，换一换节奏。

## 发现三：告诉它记忆是干什么用的，别规定怎么写

在 CL-Bench 上，研究者只是告诉 Claude"有一个记忆文件夹可以用"。对 Opus 4.7 和 Opus 5 来说，这就够了，成绩明显提升。

他们又试了加一条具体规则，比如"只记录失败的经验"。结果 Opus 4.7 和 Opus 5 都丢掉了记忆带来的大部分提升。对强模型来说，让它自己判断什么重要，比提前定死规则好。

不过，老模型确实需要引导。Sonnet 4.6 经常不读自己的记忆，也不验证自己的猜想。提示它"答题前先读记忆，并且验证你的猜想"以后，分数接近翻倍。而 Sonnet 5 不用提示，10 次里有 9 次会主动先读记忆；Sonnet 4.6 连一半都不到。

## 发现四：笔记会写错，要拿原始记录来对

笔记是当场写的，可能一开始就错了，也可能随着环境变化慢慢过时。之后的会话读到它，会直接相信。

游戏里有一段要穿过月见山，这是一个山洞：入口在西边，出口在东边。入口附近有一个陷阱，一道只能往下跳、跳下去就回不来的台阶，会把人送回来时的路。Claude 拿山脚的宝可梦中心当地标，而这个中心其实在入口那一侧，也就是西边。

它却在笔记里写成了东边。于是走出宝可梦中心时，它以为山已经穿过了，还更新笔记写"月见山完成"。几步之后，它从台阶跳下去，回到了来时的路。它没意识到是自己弄反了，反而认为是"往西走过头了"。

没有纠正的那一次，它这样掉回去了三次，第三次后说想停下来，不想再绕圈了。实验设置让它继续，它就一路退回上一座城市，最后也没到达下一座城市。

而先跑一次 Dreaming，让它拿笔记去对照原始会话记录，它马上发现了地标写反了，并改正了笔记。带着改过的笔记，它直接回到山洞，最后到了下一座城市。

原始记录在这里就是"事实依据"。只整理笔记、不回头对原始记录，错误会被一直带下去。

## 发现五：Wiki 是地图，但不是越详细越好

Dreaming 还可以把零散的笔记整理成 Wiki：一组由 Claude 自己写、自己维护的页面，每页讲一件事，并且互相链接。它的作用像一张地图，帮 Claude 在越来越多的记忆里快速找到东西。

**Wiki 和搜索配合效果最好。** 测试用的是 Stainless（Anthropic 今年 5 月收购的一家软件公司）的内部文档，大约 35 万个文件、4.2 亿 token，配 25 道题。Dreaming 从 2 轮做到 128 轮，只看 Wiki 答题的得分从 13% 涨到 48%。Wiki 加搜索一起用，得分从 54% 涨到 61%，而只用搜索是 53%。一起用还让每道题省了大约 2 万 token。

**答案越需要跨文档拼起来，Wiki 越有用。** 在一组关于公司合并的 24 道题里，一半以上要综合好几份文档才能答，Wiki 版得分 87%，只用搜索是 73%。但在另一个法律文书任务里，大部分要点从单份文档里就能搜到，Wiki 就没有明显帮助。

还有两个坑：

- **地图画成了疆域那么大。** 在一个法律任务里，Wiki 写得比原始文档本身还大，等于什么都没有提炼。文章拿博尔赫斯的短篇《论科学的精确性》作比：那篇故事里的地图画得太精细，大到和它描绘的帝国一样大。
- **多个 Agent 同时写一张表，会互相覆盖。** 在一个整理合同条款的任务里，几个 Agent 同时往一张共享表格里写，最后 57 个关键事实只保住了 41 个（72%）。后来让 Claude 反思失败、自己改写建 Wiki 的指令：每份合同单独一页，由一个 Agent 负责，条款逐字引用、不做概括。改完以后，57 个全部保住了。

## 最上面那一层，要小

每次会话自动加载的那部分记忆，好处是 Claude 不用去找，甚至不用知道有东西可找。但它很贵：每次都占 token，一条错误的笔记也会被带进每一次会话。而且加载了不等于会照做，Claude Code 的文档就提醒过，指令文件越长，模型越不容易遵守。

所以最上面这一层必须保持很小，Dreaming 的一大工作就是把细节往下挪，只留一个链接。Claude Code 的自动记忆就是这么做的：每次只加载 `MEMORY.md` 的前 200 行或前 25KB，它只是一个索引，告诉 Claude 自己知道什么、去哪里找。

## 文章留下的几个问题

- **什么时候记？** 干活时当场记，能抓住当下的重点，但会分散注意力。放到 Dreaming 里记，不打扰干活，但整理出来的东西不能马上用。
- **怎么让记忆一直是对的？** 笔记可能一开始就错，也可能慢慢过时。Dreaming 能纠错，但要花算力，不可能把所有记忆一直反复检查，可能更应该重点检查容易变的内容，或者根据记忆被读取的频率来调整整理的节奏。
- **要不要干脆以搜索原始记录为基础？** Wiki 加搜索有时效果更好，但维护 Wiki 本身也要算力，还得防止它积累错误甚至编造的内容。

## 我自己的收获

读完我给自己记了四条，用在自己搭 Agent 或者用 Claude 的时候：

1. **只记推出来的东西。** 记策略、失败的教训、验证过的规则和用户的偏好。代码、界面、数据库里随时能查到的状态，不要往记忆里塞。
2. **整理记忆时要回头对原始记录。** 只压缩、不核对，错的笔记会被一遍遍强化。
3. **每次自动加载的记忆要有硬上限。** 只放最常用的规则，以及下层文件的索引。
4. **大量资料用"Wiki + 搜索"两条腿走路。** Wiki 负责指路、省 token，搜索负责兜底、不丢细节。

最打动我的，还是开头那个判断：好的记忆不是把过去全部存下来，而是对未来要用什么做一个准确的预测。预测难免出错，所以还要经常停下来，拿事实回头看一看。
